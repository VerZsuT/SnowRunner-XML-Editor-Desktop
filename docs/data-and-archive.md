# Данные, архив и обновления

## Каталоги данных

Каталог выбирается при старте ([paths.rs](../src-tauri/crates/app/src/paths.rs)):

| Режим | Условие | Каталог данных |
|---|---|---|
| `installed` | обычный запуск | `%APPDATA%\SnowRunner XML Editor` |
| `portable` | рядом с `.exe` есть `portable.txt` | `<каталог exe>\data` |
| `dev` | `tauri dev` | `%APPDATA%\SnowRunner XML Editor` |

Маркер `portable.txt` создаётся переключателем в окне настроек; в режиме разработки
переключение запрещено. Смена режима копирует только `jsons/*.json` и не переносит
`mainTemp`, `modsTemp` и бэкапы.

```text
<data_root>/
  jsons/
    config.json          конфигурация
    favorites.json       избранные файлы
    edited.json          изменённые файлы
    edited-documents.json  журнал полей сохранённых документов
    mods.json            установленные моды
    archive.json         отпечаток распакованного архива
  mainTemp/              распакованные файлы основной игры/DLC
    [media]/classes/...
    [media]/_templates/...
    [media]/_dlc/...
    [strings]/...
  modsTemp/<мод>/        распакованные файлы мода
  backups/
    initial.pak          основной бэкап
    initial_<suffix>.pak датированный бэкап (если передан suffix)
    previous_initial/    копия mainTemp до перечитывания изменившегося архива
  updateTemp/            загруженный установщик или zip
```

## Отпечаток архива

`jsons/archive.json` хранит `path`, `size`, `modifiedMs` и `centralCrc` — CRC32
канонического представления записей central directory `initial.pak`. Отпечаток пишется
после распаковки и после пересборки архива; локальные заголовки и содержимое файлов
при его расчёте не читаются, поэтому проверка многогигабайтного архива дешёвая.

| Состояние | Условие |
|---|---|
| `ok` | путь, размер, время изменения и CRC совпали |
| `changed` | любое расхождение: архив заменили снаружи или игра обновилась |
| `unknown` | отпечатка нет, файла архива нет, JSON битый или central directory не читается |

В состоянии `changed`/`unknown` запись в основной архив запрещена: сохранение документа
и обновление архива возвращают ошибку `archiveChanged`, а интерфейс показывает окно
«Перечитать архив». Моды не блокируются: у них отдельные `.pak`.

## `initial.pak`: распаковка

1. Пользователь выбирает `initial.pak`; путь сохраняется в `config.json`.
2. `unpack_initial` открывает архив и извлекает записи по встроенному списку:
   `main`, `optimized` (используется интерфейсом) или `mods`.
3. Файлы пишутся в промежуточный каталог `mainTemp.new-<pid>`, затем каталог
   подменяет прежний `mainTemp` одной операцией переименования.
4. Прежний `mainTemp` удаляется; `refresh_archive` (меню «Распаковать архив»)
   сначала переименовывает его в `backups/previous_initial`, поэтому старые файлы
   не попадают в пересборку, но остаются для восстановления правок.
5. После успеха пишется отпечаток, реестр открытых документов и кэш шаблонов
   очищаются (`Documents::clear`), окно перезагружается.
6. В первоначальной настройке перед первой распаковкой вызывается бэкап; в пустом
   состоянии списка распаковка идёт **без бэкапа**.

Списки лежат в [crates/app/lists](../src-tauri/crates/app/lists) и встроены в бинарник
через `include_str!`. Это данные, а не WinRAR-специфика.

## `initial.pak`: обновление

`update_archive`:

1. Проверяет отпечаток (`require_unchanged`): изменившийся архив не пересобирается.
2. Проверяет, что архив и каталог существуют; каталог не пуст.
3. Собирает файлы каталога рекурсивно; имя записи — относительный путь с `\`.
4. Сравнивает каждый файл с записью архива по CRC32 и размеру.
5. Изменённые записи пересобирает, неизменённые копирует сжатым потоком.
6. Новые записи добавляет в конец; маркер `edited` не добавляется и не удаляется —
   старый маркер 1.x остаётся в архиве как есть.
7. Атомарно заменяет архив и записывает новый отпечаток (mtime и CRC архива меняются
   законно).

Следствия:

* архив пересобирается целиком, даже если изменений нет; маркер `edited` больше не нужен:
  признак правки — обновлённый отпечаток архива;
* старый маркер `edited` сохраняется (zip-слой не удаляет записи) и читается только как
  диагностика `markerPresent` в `archive_status`; ни одно решение от него не зависит;
* порядок существующих записей и их метаданные сохраняются;
* метод сжатия изменённой записи сохраняется (stored или deflate);
* zip64 и шифрование отвергаются при чтении; архив с data descriptor читается, но пересборка с такими записями отклоняется;
* бэкап автоматически не создаётся. Пункт «Бэкап» верхнего меню — отдельное действие.

Для мода каталог — `modsTemp/<мод>`, имя мода проверяется на пустоту, `..`, `/`, `\`, `:`
и в команде, и при загрузке `mods.json`.

## Сохранение документа

`save_document`:

1. Проверяет отпечаток основного архива (для документа без мода) — до записи файла
   и снятия `dirty`.
2. Читает старый файл документа с диска и собирает разрешённые редактором поля —
   снимок `disk`. Если файл не читается или у вида нет списка полей, журнал для
   документа не обновляется.
3. Берёт XML-дерево из памяти Rust.
4. Форматирует: 2 пробела, CRLF, самозакрывающиеся пустые теги.
5. Кодирует в исходной кодировке с исходным BOM и объявлением.
6. Пишет атомарно в исходный файл (в `mainTemp` или `modsTemp`).
7. Обновляет журнал полей (`changes::merge_saved`) и пополняет `edited.json` для
   траков и прицепов (`mark_edited`).
8. Сразу пересобирает соответствующий `.pak`: `initial.pak` для файлов основной игры
   или `.pak` мода из `mods.json`.

Для основного архива проверка отпечатка идёт **до** записи документов и снятия `dirty`:
если архив изменился, файлы не пишутся, а UI показывает окно перечитывания. После
пересборки отпечаток обновляется.

Бэкап автоматически не создаётся. `save_document` обновляет архив своего документа,
`save_all_documents` — архивы всех открытых документов (`force = true` — и без правок),
поэтому импорт `.epf` тоже сразу попадает в игру. Сброс к значениям по умолчанию
меняет документ только в памяти и попадает в архив после сохранения.

Форматирование нормализует файл: побайтовый diff может быть большим, даже если изменено
одно значение. Это ожидаемо.

## Журнал полей

Журнал `<data_root>/jsons/edited-documents.json` ведётся с 2.0.0 и хранит историю
полей, которые пользователь менял в редакторе. Он нужен восстановлению после
обновления игры: только по нему видно, какие значения принадлежат пользователю,
а какие — новой версии игры. Отдельной команды у журнала нет: его пишут
`save_document`/`save_all_documents` и сценарий восстановления; сброс к
первоначальному состоянию удаляет файл.

Список полей задан явно для каждого вида документа в
`crates/domain/src/game/editable.rs`: путь элемента (`Any`/`Prefix`/`Exact`),
атрибут и ключ подписи из `FIELD_TEXTS`. Служебные атрибуты структуры аддонов
и элементы `_templates` в журнал не попадают.

### Формат

```json
[
  {
    "kind": "engines",
    "name": "engine_a",
    "archiveName": "[media]\\classes\\engines\\engine_a.xml",
    "fields": [
      { "selector": "/EngineVariants/Engine", "attribute": "Torque", "base": "100000", "value": "120000" },
      { "selector": "/EngineVariants/Engine", "attribute": "BrakesDelay", "base": null, "value": "0.2" }
    ]
  },
  {
    "kind": "truck",
    "name": "ank_mk38",
    "archiveName": "[media]\\classes\\trucks\\ank_mk38.xml",
    "fields": []
  }
]
```

* `EditedDocument { kind, name, archiveName, fields }`; `archiveName` — точный путь
  записи архива, по нему журнал находит документ и при сохранении, и при
  восстановлении.
* `EditedField { selector, attribute, base, value }`; `base` — значение до первой
  правки пользователя, `value` — сохранённое; `null` — атрибута нет (удалён или
  отсутствовал).
* Поле уникально парой `(selector, attribute)`.
* Документ уникален `archiveName` без учёта регистра; повторная запись заменяет
  набор `fields`.
* Пустые `fields` — «история есть, правок нет»: документ в журнале есть, но
  восстанавливать нечего. Отсутствие документа — «истории нет» (1.4.0 и ранняя 2.0.0).
* Журнал не участвует в `list_edited` и списке «Изменённые». `unmark_edited` для
  трака/прицепа удаляет и запись журнала с тем же именем: иначе осталась бы
  осиротевшая история.

### Слияние при сохранении

Команда сохранения сравнивает три снимка: `disk` — файл на диске до записи,
`tree` — сохраняемое дерево и текущую запись журнала `(base, value)`. Для каждого
поля из объединения `disk ∪ tree ∪ журнал`:

| Условие | Действие |
|---|---|
| запись есть, `tree == base` | пользователь вернул значение к базе — запись удаляется |
| запись есть, `tree == disk` | поле в этой записи не менялось — запись не трогается |
| запись есть, `tree != disk`, `disk == value` | на диске предыдущее сохранение пользователя — `value = tree`, `base` не сдвигается |
| запись есть, `tree != disk`, `disk != base` | на диске уже другая версия игры — `base = disk`, `value = tree` (правка заменяет старую) |
| запись есть, `tree != disk`, иначе | `value = tree`, `base` сохраняется |
| записи нет, `tree != disk` | добавляется `{ base: disk, value: tree }` |
| записи нет, `tree == disk` | ничего не добавляется |

Документ записывается в журнал даже с пустыми `fields`. Для траков и прицепов
дополнительно вызывается `mark_edited`, как раньше; для остальных видов — только
журнал. Следствие: после обновления игры отложенная правка сдвигает базу на новую
версию игры для этого поля, а возврат к исходному значению удаляет запись.

## Восстановление после обновления игры

Запуск — из окна целостности после «Перечитать архив» или вручную из меню
«Бэкап → Восстановить параметры после обновления игры». Восстановление блокирующее:
одно за раз, при несохранённых документах запуск отклоняется (`conflict`).

### Что восстанавливается

| Источник | Что | Поля |
|---|---|---|
| `edited.json`, запись без `mod` | файл трака или прицепа (база или DLC) | записи журнала по `archiveName`; если их нет — режим «нет истории» |
| `edited-documents.json`, запись без `mod` | сохранённый документ: двигатель, коробка, подвеска, лебёдка, колёса, аддон, трак/прицеп | `fields[]` журнала |
| `mod` в `edited.json` | не восстанавливается | — |

Кандидат с совпадающими старым и новым файлами не показывается: восстанавливать
нечего. Если файл перемещён или удалён игрой, точный путь не находится — документ
попадает в «пропущено», одноимённые файлы в других каталогах не перебираются.
Действия (краны, прицепы, «Банан бандита») в 3-way не входят: они только добавляются,
если их нет в новом файле.

### Трёхстороннее сравнение

```text
base  — значение до первой правки пользователя (из журнала);
ours  — сохранённое значение (value в журнале);
theirs — значение в новом файле игры.
```

| Условие | Действие |
|---|---|
| `theirs == base` | игра поле не меняла → применить `ours` |
| `theirs == ours` | уже совпадает → пропустить, запись журнала убрать |
| иначе | конфликт: пользователь выбирает «Моё» или «Игры» |

`null` означает отсутствие атрибута. Если элемента (`selector`) в новом файле нет,
поле показывается как пропущенное, а не конфликт. Поля, которых нет в журнале, не
читаются и не меняются: значения игры в них сохраняются. Без решения по каждому
конфликту применить нельзя; «Моё для всех» и «Игры для всех» разрешают все конфликты.

### После восстановления

* поле применено или конфликт решён в пользу «Моё» → `base = значение игры до применения`,
  `value = моё`;
* конфликт решён в пользу «Игры» или поле уже совпало → запись удаляется;
* поле не найдено в новом файле → запись остаётся (элемент может вернуться);
* файл с ошибкой или отменённый — запись не трогается; исключение — режим «нет истории»:
  ему пишется пустая история, чтобы окно не спрашивало о файле снова.

Так база соответствует версии игры, в которую применяли, и следующий конфликт
считается правильно.

### Режим «нет истории»

Для траков и прицепов 1.4.0/ранней 2.0.0 журнала нет: окно показывает отличающиеся
поля старого и нового файлов и спрашивает по файлу, восстанавливать ли поля из
старого файла целиком. Это грубый fallback: очищенные значения не восстанавливаются,
а изменения игры в тех же полях могут быть перезаписаны. После решения (восстановить
или пропустить) файл записывается в журнал, чтобы окно не спрашивало о нём снова:
при восстановлении для каждого отличавшегося поля `base` = значение нового файла до
применения, `value` = значение старого; при пропуске — пустая история («история есть,
правок нет»). Связанные документы и аддоны без истории не восстанавливаются.

### `previous_initial` и маркер `edited`

* Восстановление читает старые файлы из `backups/previous_initial` — копии `mainTemp`,
  сделанной при перечитывании изменившегося архива. Хранится одно поколение: следующее
  перечитывание заменяет копию, оба окна об этом предупреждают. Удалить копию можно
  командой `discard_previous` (кнопка «Удалить копию»); после успешного восстановления
  без ошибок и отмены она удаляется автоматически.
* Маркер `edited` в архив больше не пишется. Старые маркеры не удаляются и остаются
  только диагностикой (`markerPresent`); 1.4.0, запущенная после 2.0.0 на
  пересобранном архиве, может показать ложное окно «обновление» — это принятое
  ограничение перехода.
* Списки распаковки `unpack-list.lst`/`unpack-list-optimized.lst` больше не содержат
  строки `edited`: пустой файл не попадает в `mainTemp`.

## Бэкапы и восстановление

| Действие | Поведение |
|---|---|
| `backup_archive(path, null)` | копия в `backups/initial.pak`, перезапись |
| `backup_archive(path, suffix)` | копия в `backups/initial_<suffix>.pak` |
| `restore_backup(path)` | атомарно копирует **только** `backups/initial.pak` поверх архива |

`backup_archive` безопасен в любом состоянии: копия текущего файла полезна всегда.
`restore_backup` отпечаток не перезаписывает, поэтому после восстановления обычно
возникает состояние `changed`: распаковка осталась от прежнего архива, и окно предлагает
перечитать архив. Если содержимое копии и архива совпадает, состояние остаётся `ok`.

Датированные бэкапы не восстанавливаются из UI: их нужно скопировать в `initial.pak` вручную.
Перед восстановлением закройте игру.

## Моды

`find_mods` ищет `.pak` в `Documents/My Games/SnowRunner/base/Mods/.modio/mods`
(включая перенаправленный в OneDrive `Documents`) и на один уровень вложенности.

`add_mod`:

1. Проверяет, что `.pak` существует.
2. Формирует имя: `sanitize_name` (пробелы → дефис, запрещённые символы удаляются,
   точки схлопываются, обрезка до 80 символов, зарезервированные имена Windows получают `_`).
3. Распаковывает в `modsTemp/.<имя>.unpack` по списку `mods`.
4. Требует каталог `classes`; иначе удаляет промежуточный каталог и возвращает ошибку.
5. Подменяет прежний `modsTemp/<имя>`: старый каталог переименовывается в
   `modsTemp/.<имя>.old`, новый занимает его место и старый удаляется. Сбой на любом шаге
   оставляет рабочий мод на месте — битый `.pak` не уничтожает уже распакованные файлы.
6. Сохраняет запись в `mods.json`.

`remove_mod` убирает запись из `mods.json`, но **не удаляет** `.pak` и `modsTemp/<имя>`.
`sync_mods` удаляет записи с пропавшими `.pak` и пересобирает распаковку, если каталога
`modsTemp/<мод>` нет или размер `.pak` изменился. Сравнение только по размеру: мод,
изменённый с тем же размером, не пересоберётся.

Файлы мода открываются как обычные документы; сохранение идёт в `modsTemp/<имя>`,
после чего `.pak` мода пересобирается автоматически. `update_archive(path, modName)`
остаётся ручным вариантом для меню.

## Игровые переводы

`game_texts(lang)` читает:

* `mainTemp/[strings]/strings_<язык>.str` — основная игра;
* `modsTemp/<мод>/texts/strings_<язык>.str` — моды.

Формат — UTF-16LE, по строке `ключ "значение"`. Приоритет: строки мода, затем игры.
Если файла нет, остаются ключи и имена файлов.

## `.epf`: обмен параметрами

Формат версии 3.0 — JSON:

```json
{
  "version": "3.0",
  "info": [{ "name": "ank_mk38", "isTrailer": false, "dlc": null, "mod": null }],
  "data": { "<имя>_<источник>": { "/Truck/TruckData": { "FuelCapacity": "200" } } },
  "actionsData": { "<имя>_<источник>": { "cranes": {}, "trailers": {} } }
}
```

* экспорт идёт из дерева в памяти, сохранять документ перед экспортом не нужно;
* экспорт дополняет совместимый файл и заменяет файл другой версии;
* импорт проверяет версию и запись `info`, применяет известные атрибуты, неизвестные пути
  пропускает, добавляет недостающие краны/прицепы;
* работают только с документами трака или прицепа;
* импорт меняет `revision` один раз, если применил хотя бы одно изменение.

## Обновление программы

`check_update`:

1. Если `checkUpdates = false` и `force = false` — выходит.
2. Читает `<pages>/version-info.json` (HTTPS, таймаут 10 с, ответ ≤ 64 КиБ).
3. Сравнивает версии по числам и суффиксу; возвращает новую версию или `null`.

`download_update`:

* проверяет версию по формату и собирает URL
  `<releases>/v<версия>/SnowRunnerXMLEditor.exe` или `SnowRunnerXMLEditor.zip`;
* качает в `updateTemp`, сообщает прогресс событием `update-progress`;
* таймаут соединения 30 с, общий — 10 минут.

`run_installer`:

* требует, чтобы файл лежал внутри `updateTemp` (канонизация путей);
* установщик запускается, портативный zip открывается в проводнике;
* приложение закрывается.

Подписи и хеш загруженного файла не проверяются: доверие строится на HTTPS и GitHub Releases.

## Что делать при сбое

| Симптом | Проверить |
|---|---|
| «Игра не видит изменений» | сохранён ли документ; архив обновляется при сохранении |
| Архив не читается | восстановить `backups/initial.pak`; если копии нет — проверить файлы игры |
| Окно «Архив изменился» после обновления игры | «Перечитать архив»: новый `mainTemp`, прежний — в `previous_initial` |
| После обновления игры пропали мои параметры | «Бэкап → Восстановить параметры после обновления игры»: поля из журнала переносятся в новую версию, изменения игры не затираются |
| После обновления игры странные данные | перечитать архив; удалять `mainTemp` вручную больше не нужно |
| Мод не обновился | сравнить размеры `.pak`; удалить `modsTemp/<мод>` и добавить заново |
| Обновление не предлагается | `site/version-info.json`, наличие файлов в GitHub Releases, HTTPS |

См. также [limits.md](limits.md) — там перечислены ограничения, которые влияют на эти сценарии.
